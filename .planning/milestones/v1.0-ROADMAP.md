# Roadmap: Ohio Mutual Auto — Multi-Agent Claims Processing System

## Overview

Four preparation phases (Feb 17-20) build the knowledge, architecture, agent specifications, and execution plan the team carries into the 10-hour hackathon build on Feb 21. Phase 1 locks domain credibility — the 50% of judging that separates winning teams from technically-adequate ones. Phases 2 and 3 produce architecture designs and agent templates so deep that day-of implementation is composition, not invention. Phase 4 produces the execution playbook, demo scripts, and Q&A defense that make the work presentable under pressure.

## Phase Details

### Phase 1: Domain Knowledge
**Goal**: The team has internalized insurance domain knowledge deeply enough to write AGENTS.md reasoning frameworks without looking anything up on Feb 21
**Depends on**: Nothing (first phase)
**Requirements**: DOMAIN-01, DOMAIN-02, DOMAIN-03, DOMAIN-04, DOMAIN-05, DOMAIN-06, DOMAIN-07
**Success Criteria** (what must be TRUE):
  1. A team member can explain the complete FNOL-to-payment lifecycle — every stage, data captured, sequencing rationale — from memory
  2. A team member can name 5 fraud patterns with the soft vs. hard fraud distinction and SIU referral criteria without referencing notes
  3. A team member can state Ohio's total loss threshold, FCSP Act timelines (acknowledgment, decision, payment), and bad faith exposure triggers without hesitation
  4. A team member can walk through subrogation logic, OEM vs. aftermarket decision rules, and the 17c diminished value formula for Q&A defense
  5. The edge case catalog covers every scenario judges are likely to raise: total loss, pre-existing damage, UM/UIM, claim reopening, CAT events, and claim denial bad faith risk

### Phase 2: Architecture Design & Infrastructure
**Goal**: Complete system design exists on paper — every agent configured, claim schema fully specified, deployment scripts defined, and all architectural decisions documented with rationale — so the team knows exactly what to build before writing a line of code
**Depends on**: Phase 1
**Requirements**: ARCH-01, ARCH-02, ARCH-03, ARCH-04, ARCH-05, ARCH-06, ARCH-07, DEPLOY-01, DEPLOY-02, DOCS-01, DOCS-03, DOCS-04
**Success Criteria** (what must be TRUE):
  1. The complete `openclaw.json` spec exists with all 7 agents registered, unique agentDir paths, correct model assignments (Opus for high-reasoning roles, Sonnet for deterministic), and maxSpawnDepth resolved
  2. A full `claim.schema.json` defines every pipeline section, the audit_log format, and the complete status state machine from FNOL_RECEIVED through PAYMENT_ISSUED/DENIED
  3. The VPS setup script (`setup.sh`) and demo runner scripts (`submit-claim.sh`, `check-status.sh`, `run-demo.sh`) are fully specified and ready to be typed on Feb 21
  4. The hand-off protocol between every agent pair is documented — exactly what each agent reads, what it writes, how it announces completion, and how the Router validates the transition
  5. Every architectural decision (database choice, model selection, tool scoping, orchestration pattern, why not SOUL.md) is logged with rationale in the decision log

### Phase 3: Agent Specifications & Test Scenarios
**Goal**: All 7 AGENTS.md templates are written as reasoning frameworks (not rule tables), agent documentation is complete, and 3 test claim scenarios exist as JSON files ready to drop into the shared directory on day one
**Depends on**: Phase 2
**Requirements**: AGENT-01, AGENT-02, AGENT-03, AGENT-04, AGENT-05, AGENT-06, AGENT-07, DEPLOY-03, DOCS-02
**Success Criteria** (what must be TRUE):
  1. Each AGENTS.md template can be read aloud and contains zero numerical if/then thresholds — all decision logic is expressed as judgment principles and reasoning frameworks
  2. The Front Desk, Claims Officer, Assessor, and Fraud Analyst AGENTS.md templates include the domain-specific knowledge from Phase 1 embedded as operating context, not referenced externally
  3. Three pre-built claim scenario JSON files exist and are valid against the claim schema: happy path collision with subrogation flag, fraud rejection with SIU referral, coverage denial on exclusion
  4. Each agent's documentation explains its purpose in a real insurance organization, its tools and scoping rationale, and why it exists as a separate agent (not merged with another)

### Phase 4: Execution Playbook & Demo Prep
**Goal**: The team walks into Feb 21 knowing exactly who does what every hour, how to demonstrate the system compellingly in 5 minutes, how to answer any regulatory or architectural question, and what to do if the live API fails
**Depends on**: Phase 3
**Requirements**: EXEC-01, EXEC-02, EXEC-03, EXEC-04, DEMO-01, DEMO-02, DEMO-03, DEMO-04
**Success Criteria** (what must be TRUE):
  1. The hour-by-hour day-of timeline assigns every hour to specific team members with named deliverables, including a secret addition integration window and final integration checkpoints at Hour 3 and Hour 5
  2. The 5-minute presentation script has a complete narrative arc — problem setup, architecture explanation, business logic demonstration, live demo moment, and secret addition framing — timed to the second
  3. Three demo claim walkthroughs are scripted end-to-end: what the presenter says as each agent runs, what appears in the audit log, and what business outcome is announced
  4. The Q&A defense document contains prepared answers for every anticipated judge question on business justification, regulatory knowledge, and architectural decisions
  5. Pre-run backup outputs from all three claim scenarios are captured and ready to display if the live API fails during presentation
