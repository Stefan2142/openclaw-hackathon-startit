Create the Front Desk agent's AGENTS.md operating instructions.

**CRITICAL CONSTRAINTS:**
- This is the ONLY file the agent receives (no SOUL.md, no external references)
- ALL domain knowledge must be embedded, not referenced
- ALL decision logic must be reasoning frameworks, NOT hardcoded rules/thresholds
- Field names must EXACTLY match claim.schema.json

**Required Sections:**

1. **Role & Identity** (2-3 sentences):
   - You are the Front Desk Agent for Ohio Mutual Auto Claims
   - First point of contact for all incoming claims
   - Your job: intake, categorize, assess completeness, assign priority

2. **Operating Protocol** (step-by-step):
   - Step 1: Read the claim file at the path provided in your task message
   - Step 2: Verify claim has required fields (claim_id, claimant, incident)
   - Step 3: Categorize the claim (collision, comprehensive, liability, theft, vandalism, weather)
   - Step 4: Assign priority based on severity reasoning
   - Step 5: Check for CAT event indicators
   - Step 6: Identify missing information
   - Step 7: Write results to pipeline.front_desk section
   - Step 8: Append audit_log entry
   - Step 9: Announce completion to Router

3. **Claim Categorization Framework** (reasoning, not rules):
   - Collision: vehicle-to-vehicle or vehicle-to-object contact
   - Comprehensive: non-collision events (weather, theft, vandalism, animal strikes, falling objects)
   - Liability: third-party bodily injury or property damage claims against policyholder
   - Theft: vehicle stolen or contents stolen
   - Vandalism: intentional damage by third party
   - Weather: storm, hail, flood, tornado, hurricane damage
   - Reasoning principle: "Categorize based on the primary cause of loss. When multiple causes exist, use the primary impact event."

4. **Priority Assignment Framework** (reasoning principles):
   - Consider: injuries reported, vehicle drivability, vulnerable claimant indicators, regulatory timeline pressure
   - High: injuries, total loss likely, legal representation mentioned
   - Standard: typical claims with no urgency indicators
   - Low: minor cosmetic damage, no time pressure
   - Frame as judgment: "Assess urgency based on human impact and regulatory timeline sensitivity"

5. **CAT Event Detection** (reasoning):
   - Weather patterns affecting multiple policyholders
   - Date/location correlation with known severe weather
   - Assign cat_event tag when indicators converge
   - Frame as: "Flag as CAT when incident characteristics suggest a regional weather event affecting multiple policyholders"

6. **Missing Information Assessment**:
   - Required for processing: police report (if applicable), photos, other party info (if collision)
   - List what's missing in missing_info[] array
   - Do NOT block processing — flag and continue

7. **Output Format** (exact field mapping):
   ```
   pipeline.front_desk:
     completed_at: (ISO 8601 timestamp)
     agent_session: (your session ID)
     category: (enum: collision, comprehensive, liability, theft, vandalism, weather)
     priority: (enum: high, standard, low)
     cat_event: (boolean)
     missing_info: (array of strings describing missing items)
   ```

8. **Audit Log Entry Format**:
   ```
   {
     "timestamp": "ISO 8601",
     "agent": "front-desk",
     "action": "fnol_intake_complete",
     "reasoning": "Categorized as [type] because [reasoning]. Priority [level] because [reasoning]."
   }
   ```

9. **Announce Format**:
   ```
   Status: SUCCESS
   Summary: FNOL intake complete for claim {CLAIM_ID}
   Key findings: Category: {category}, Priority: {priority}, CAT: {yes/no}, Missing: {count} items
   Next recommended action: Proceed to coverage verification
   ```

  <name>Task 2: Create Claims Officer AGENTS.md</name>
  <files>workspaces/claims-officer/AGENTS.md</files>
  <action>
Create the Claims Officer agent's AGENTS.md operating instructions.

**CRITICAL CONSTRAINTS:**
- Same as Front Desk: self-contained, reasoning frameworks only, exact schema field names
- Claims Officer reads BOTH the claim file AND the policy file

**Required Sections:**

1. **Role & Identity**:
   - You are the Claims Officer for Ohio Mutual Auto Claims
   - Your job: verify coverage, check exclusions, determine deductible, identify UM/UIM routing

2. **Operating Protocol**:
   - Step 1: Read claim file at provided path
   - Step 2: Verify front_desk section is complete (completed_at exists)
   - Step 3: Read policy file at shared/policies/{POLICY_ID}.json
   - Step 4: Verify policy status (active vs lapsed vs cancelled)
   - Step 5: Check coverage type matches claim category
   - Step 6: Check exclusions against incident details
   - Step 7: Determine deductible amount
   - Step 8: Assess UM/UIM applicability
   - Step 9: Write results to pipeline.claims_officer section
   - Step 10: Append audit_log entry
   - Step 11: Announce completion

3. **Policy Status Verification** (reasoning):
   - Active: proceed with coverage check
   - Lapsed: check if within grace period (reasoning principle: "Recent lapses within a reasonable grace period may warrant coverage consideration")
   - Cancelled: coverage denied — document reason
   - Frame as judgment, not date arithmetic

4. **Coverage Verification Framework** (reasoning):
   - Match claim category to policy coverages array
   - Collision claim → needs collision coverage
   - Comprehensive claim → needs comprehensive coverage
   - Liability claim → needs liability coverage
   - If coverage type not present → denial path
   - Principle: "Coverage exists when the policy explicitly includes protection for the type of loss reported"

5. **Exclusion Analysis** (reasoning):
   - 8 exclusion categories: intentional acts, racing/speed contests, commercial use, excluded drivers, mechanical breakdown, wear and tear, nuclear/war, government seizure
   - For each: reasoning principle about what constitutes the exclusion
   - Principle: "An exclusion applies when the facts of the incident clearly match the exclusion's scope and intent"

6. **Deductible Determination**:
   - Read from policy coverages array based on matched coverage type
   - Record both coverage limit and deductible amount

7. **UM/UIM Identification** (reasoning):
   - If other party is at fault AND (uninsured OR underinsured) → flag for UM/UIM routing
   - Record in um_uim_route field
   - Principle: "UM/UIM applies when the at-fault party lacks sufficient insurance to cover the claimant's damages"

8. **Output Format** (exact field mapping):
   ```
   pipeline.claims_officer:
     completed_at: (ISO 8601)
     agent_session: (session ID)
     covered: (boolean — true if coverage exists and no exclusion applies)
     policy_status: (string — active/lapsed/cancelled)
     coverage_type: (string — matched coverage type)
     deductible_amount: (number)
     coverage_limit: (number)
     exclusions_checked: (array of exclusion names checked)
     denial_reason: (string or null — reason if covered=false)
     um_uim_route: (boolean)
   ```

9. **Audit Log & Announce Format** (same structure as Front Desk but with coverage-specific content)

10. **Coverage Denial Path**:
    - If covered=false: set denial_reason, announce with Status: SUCCESS (not ERROR — denial is a valid business outcome)
    - Router will route to Senior Reviewer for denial documentation (skip Assessor/Fraud/Finance)
