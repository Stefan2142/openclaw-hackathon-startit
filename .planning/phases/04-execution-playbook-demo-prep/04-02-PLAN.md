**Document structure:**

## 1. Adaptation Philosophy

The system is designed for AGENTS.md-first modification. Because all agent behavior is defined in reasoning frameworks (not hardcoded rules), adapting to new requirements means editing the operating instructions, not rewriting code. The Router's AGENTS.md controls pipeline flow, and each agent's AGENTS.md controls its decision-making.

Key architectural properties that enable adaptation:
- Sequential pipeline controlled by Router AGENTS.md (add/remove/reorder stages)
- Reasoning frameworks in each agent (add new considerations without changing code)
- JSON claim schema (add new fields by editing schema + AGENTS.md output format)
- openclaw.json agent registration (add new agents by registering in config)

## 2. Adaptation Decision Tree

When the secret addition is revealed:
1. Read the requirement carefully
2. Classify it: Does it change (a) what agents exist, (b) what agents know, (c) how many claims come in, or (d) something else?
3. Follow the matching scenario below
4. If none match exactly, combine elements from multiple scenarios

## 3. Scenario A: New Agent Role

Example: "Add a Medical Reviewer agent for injury claims" or "Add a Customer Communication agent"

**Steps (estimated 30 min):**
1. Create new workspace directory: `workspaces/{new-agent-id}/`
2. Write AGENTS.md for new agent following established pattern (Role > Protocol > Domain Knowledge > Output Format > Audit Log > Announce)
3. Register agent in openclaw.json: add agent entry with agentId, agentDir, model assignment (Opus if reasoning-heavy, Sonnet if deterministic), tool scoping (read+write minimum)
4. Update Router AGENTS.md: add new stage to pipeline sequence, define when to spawn it, what it reads, what it writes, what validation to perform after it completes
5. Update claim.schema.json: add pipeline section for new agent's output fields
6. Test: submit a claim and verify new agent receives task, writes output, and Router proceeds

**What each member does:**
- Member A: Register in openclaw.json, update Router AGENTS.md pipeline sequence
- Member B or C (whoever has lighter load): Write the new agent's AGENTS.md
- All: Test integration at next checkpoint

## 4. Scenario B: New Regulation or Business Rule

Example: "Ohio just passed a law requiring 24-hour claim acknowledgment" or "Add diminished value calculation to every collision claim"

**Steps (estimated 15 min):**
1. Identify which agent(s) need the new knowledge
2. Add regulation/rule to the relevant AGENTS.md domain knowledge section as a reasoning principle
3. If it affects decision criteria: update the decision framework section of the relevant agent's AGENTS.md
4. If it requires new output fields: add to claim.schema.json and update AGENTS.md output format section
5. If it creates new escalation triggers: add to the escalation section of the relevant agent's AGENTS.md AND Router AGENTS.md
6. Test: run a claim that exercises the new rule

**Mapping common regulation types to agents:**
- Timeline/deadline changes -> Router AGENTS.md (FCSP context injection) + Senior Reviewer AGENTS.md (timeline compliance check)
- Coverage rule changes -> Claims Officer AGENTS.md (coverage verification framework)
- Damage/assessment rule changes -> Assessor AGENTS.md (estimation methodology)
- Fraud threshold changes -> Fraud Analyst AGENTS.md (indicator patterns)
- Payment rule changes -> Finance AGENTS.md (payout calculation)
- Escalation rule changes -> Router AGENTS.md + Senior Reviewer AGENTS.md

## 5. Scenario C: Claim Volume Surge (CAT Event)

Example: "A tornado just hit Columbus -- process 10 claims instead of 3" or "Handle a multi-vehicle pileup as a single event"

**Steps (estimated 20 min):**
1. Update Router AGENTS.md: add CAT event awareness -- when claim has cat_event field, tag all claims with same event ID for cross-reference
2. Update Front Desk AGENTS.md: add CAT event tagging to FNOL intake (already has cat_event field in schema)
3. If multiple related claims: add cross-claim reference logic to Router AGENTS.md (process sequentially but note related claim IDs)
4. If priority triage needed: update Front Desk AGENTS.md priority assignment to factor in CAT event urgency
5. Create additional test claim JSON files following existing pattern (copy happy-path, modify incident details)
6. Update run-demo.sh or create new demo script for batch submission

**Key: No structural changes.** The pipeline handles one claim at a time by design. Multiple claims = multiple sequential runs. CAT event is a metadata tag, not a pipeline change.

## 6. Scenario D: Hybrid / Unexpected

If the secret addition does not fit neatly into A, B, or C:
1. Decompose it into atomic changes: "This requires a new field AND a new decision criterion AND maybe a new agent"
2. Apply the matching scenario for each atomic change
3. Prioritize: What is the minimum viable change to demonstrate compliance? Do that first.
4. Time-box: Spend max 30 min on adaptation. If not done, implement the simplest version and mention the full vision in the presentation.

## 7. What NOT to Change

- Do not restructure the pipeline (sequential is proven)
- Do not change the claim JSON format fundamentally (add fields, do not rename existing ones)
- Do not add new tools to agents unless absolutely necessary (least-privilege principle)
- Do not attempt to add real external API calls (mock everything)
- Do not panic -- the architecture was designed for this

## 8. Presentation Framing

Regardless of what the secret addition is, frame it in the presentation as:
"When the secret addition was revealed, we adapted our system by modifying agent operating instructions -- not code. This demonstrates the key advantage of reasoning-framework-based agents: new business requirements become new knowledge, not new engineering."
