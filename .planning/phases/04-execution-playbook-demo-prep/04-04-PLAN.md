Create docs/qa-defense.md -- prepared answers for every anticipated judge question, organized into 3 categories.

**Format:** Each question has the question text, a concise answer (2-3 sentences for spoken delivery), and a "deep dive" section with supporting evidence and references for follow-up questions.

### Category 1: Business Justification (50% of judging)

**Q: "Why 6 pipeline agents instead of 1 or 2?"**
A: Each agent maps to a real insurance role -- an intake clerk doesn't do fraud analysis, and a fraud analyst doesn't calculate payments. Separating concerns means each agent has focused domain knowledge and scoped tools (least-privilege security), and the system mirrors how real insurance companies operate. If we merged agents, we'd lose the audit trail granularity that regulators require.
Deep dive: Reference decision-log.md Decision #8 (tool scoping), agent-documentation.md separation rationale sections.

**Q: "How does fraud detection work?"**
A: The Fraud Analyst uses indicator convergence -- it looks for patterns that converge rather than checking single rules. Seven named fraud patterns (staged accidents, phantom passengers, paper accidents, inflated repair, prior damage, friendly tow, VIN switching) are embedded as reasoning frameworks. A single flag is noted; converging indicators trigger SIU referral.
Deep dive: Reference fraud-detection.md Quick Reference, Fraud Analyst AGENTS.md.

**Q: "How do you handle compliance?"**
A: Compliance is structural, not bolted on. The Router injects FCSP timeline context into every agent's task message. The Senior Reviewer checks timeline compliance before every decision. The audit log captures every agent's reasoning with regulation references. The system cannot skip a compliance check because the pipeline architecture enforces it.
Deep dive: Reference regulatory-compliance.md, Router AGENTS.md context enrichment, Senior Reviewer AGENTS.md.

**Q: "What happens when a claim is denied?"**
A: The Claims Officer identifies the coverage issue, and the pipeline shortcuts -- it skips damage assessment, fraud analysis, and payment, going directly to Senior Reviewer. The Senior Reviewer documents why the denial is defensible, assesses bad faith risk, and confirms the denial. This shortcut saves processing time while still protecting the insurer from bad faith claims.
Deep dive: Reference decision-log.md Decision #13, architecture/handoff-protocol.md denial path.

**Q: "How do you handle edge cases like total loss or pre-existing damage?"**
A: Each edge case is handled by reasoning principles embedded in the relevant agent. The Assessor knows Ohio's 100% ACV total loss threshold and flags pre-existing damage for the Fraud Analyst. The Senior Reviewer escalates to human review when edge cases exceed the system's confidence. We documented 10 categories of edge cases during preparation.
Deep dive: Reference edge-cases.md, Assessor AGENTS.md, Fraud Analyst AGENTS.md.

**Q: "What if the system makes a wrong decision?"**
A: Every decision is logged with reasoning in the audit trail. The Senior Reviewer acts as a safety net before any payment or denial. High-risk claims (fraud flags, value >$25K, total loss, legal representation) are escalated to human review. The system is designed to be conservative -- it escalates rather than guesses.
Deep dive: Reference architecture/human-in-the-loop.md escalation triggers.

### Category 2: Architecture Decisions (50% of judging)

**Q: "Why JSON files instead of a database?"**
A: For a 10-hour hackathon, every minute of infrastructure setup is a minute not spent on business logic. JSON files are zero-setup, human-readable during the demo (judges can cat the file), and natively compatible with OpenClaw's read/write tools. The sequential pipeline guarantees single-writer-per-claim, so we don't need locking. For production, we'd migrate to SQLite or Postgres.
Deep dive: Reference decision-log.md Decision #1.

**Q: "Why sequential pipeline instead of parallel?"**
A: Correctness requires it. Fraud analysis needs the damage estimate to detect inflated repair claims. The Senior Reviewer needs the fraud score to decide. Payment needs the approval. Parallelizing would either require complex synchronization or produce incorrect results. Sequential is simple, correct, and easy to debug.
Deep dive: Reference decision-log.md Decision #5.

**Q: "How does state management work between agents?"**
A: Every claim is a single JSON file. Each agent reads the file, writes to its pipeline section, and appends an audit log entry. The Router validates the output after each agent completes. This gives us a complete state snapshot at every point in the pipeline -- if something breaks, we can see exactly where and why.
Deep dive: Reference architecture/shared-state.md, architecture/handoff-protocol.md.

**Q: "Why Opus for some agents and Sonnet for others?"**
A: Cost optimization without quality sacrifice. Agents doing complex reasoning (Assessor, Fraud Analyst, Senior Reviewer, Router) use Opus. Agents doing structured data tasks (Front Desk, Claims Officer, Finance) use Sonnet. This cuts token cost roughly in half while keeping quality where it matters.
Deep dive: Reference decision-log.md Decision #2, openclaw.json model assignments.

**Q: "How do you handle errors and retries?"**
A: Each agent has a per-stage timeout (60-120 seconds depending on task complexity). If an agent fails, the Router retries up to 2 times with a fresh session. If it still fails, the claim goes to ERROR status with a full audit log of what happened. For the demo, the happy path is reliable, but the system handles failures gracefully.
Deep dive: Reference architecture/router-design.md error handling, decision-log.md timeouts.

**Q: "Why not use SOUL.md?"**
A: Sub-agents spawned via sessions_spawn do not receive SOUL.md -- they only get AGENTS.md and TOOLS.md. This is an OpenClaw architectural constraint, not a choice. All operating instructions go in AGENTS.md. We documented this explicitly so the team doesn't waste time on day one debugging why SOUL.md instructions are ignored by pipeline agents.
Deep dive: Reference decision-log.md Decision #4, openclaw-tools.md.

**Q: "How does the Router control the pipeline?"**
A: The Router uses a state machine with 9 states. It spawns each agent via sessions_spawn with an enriched task message (claim file path + prior stage results + regulatory context). After each agent announces completion, the Router reads the claim file, validates required fields, transitions the status, and decides what to spawn next -- or whether to shortcut (coverage denial) or escalate.
Deep dive: Reference architecture/router-design.md, Router AGENTS.md.

### Category 3: Regulatory Knowledge

**Q: "What are the FCSP timelines?"**
A: Ohio follows the NAIC model. Acknowledgment within 10-15 business days of receipt. Investigation decision within a reasonable time (most states interpret as 40 days). Payment within 30 days of settlement. Our system processes claims in minutes, well within all deadlines, and the Router tracks these timelines at every stage.
Deep dive: Reference regulatory-compliance.md FCSP section.

**Q: "What is the total loss threshold in Ohio?"**
A: Ohio uses 100% ACV -- a vehicle is a total loss when repair costs exceed its actual cash value. Some states use 75% or 80%, but Ohio is 100%. The Assessor knows this and flags total loss when the estimate hits ACV. Total loss claims are automatically escalated to human review by the Senior Reviewer.
Deep dive: Reference damage-assessment.md total loss section, Assessor AGENTS.md.

**Q: "What is bad faith exposure?"**
A: Bad faith occurs when an insurer unreasonably denies, delays, or underpays a claim. Common triggers: denying without investigation, missing FCSP deadlines, failing to explain denial reasons, lowballing estimates. Our system mitigates bad faith risk by: documenting every decision with reasoning, checking FCSP compliance at every stage, and escalating ambiguous cases to human review rather than auto-denying.
Deep dive: Reference regulatory-compliance.md bad faith section, edge-cases.md bad faith category.

**Q: "How does subrogation work?"**
A: When our policyholder is not at fault, we pay the claim and then pursue recovery from the at-fault party's insurer. The Finance agent identifies subrogation candidates by checking for other-party information and fault indicators. The subrogation target (insurer + policy number) is recorded in the claim for the recovery team. This reduces the net cost of the claim.
Deep dive: Reference payment-subrogation.md subrogation section, Finance AGENTS.md.

**Q: "What about diminished value?"**
A: Diminished value is the loss in a vehicle's market value after repair. The 17c formula (base value x damage modifier x mileage modifier) is the standard calculation. Our Assessor notes when diminished value may apply, and the Senior Reviewer can flag it for separate handling. For this demo, we focus on repair/total loss rather than diminished value calculation, but we can explain the framework.
Deep dive: Reference edge-cases.md diminished value section.
